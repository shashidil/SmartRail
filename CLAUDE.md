# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

SmartRail Sri Lanka: a smart-card (RFID) train ticketing demo. Two independent npm projects with no shared root package: `backend/` (Express API) and `frontend/` (React + Vite + Tailwind PWA). There is no test suite.

## Commands

Backend (port 5000, override with `PORT` in `backend/.env`):
```bash
cd backend && npm install
npm start        # node server.js
npm run dev      # nodemon, auto-restart
```

Frontend:
```bash
cd frontend && npm install
npm run dev      # Vite dev server
npm run build    # production build to frontend/dist (also emits the service worker)
npm run preview  # serves the build on :4173; use this, not dev, to exercise PWA/offline behaviour
npm run generate-pwa-assets  # regenerate icons + favicon in public/ from public/logo.svg
```
`npm run lint` is defined, but ESLint isn't installed as a dependency and there's no ESLint config, so it won't run until both are added.

Both servers must be running for the app to work (`backend/.env` needs `DATABASE_URL` and `JWT_SECRET`). Demo logins: passenger `nirmal` / `user123`, admin `admin` / `admin_rail_2024`.

## Architecture

**Backend (`backend/server.js`, ESM).** All routes live in `server.js`; database code lives in `backend/db/`. Persistence is PostgreSQL, configured by `DATABASE_URL` in `backend/.env` (gitignored; copy `backend/.env.example`). On startup `db/init.js` applies `db/schema.sql` (idempotent) and, if `users` is empty, seeds 2 users and 9 railway lines (each with a fixed fare and two stations) from `db/seed.js`; it also converts legacy routes (text `stations`, `base_fare`) to a fixed `fare` plus ordered stations, idempotently. The server exits if the database is unreachable. Top-up and the trip start/end taps each run in one DB transaction (conditional `UPDATE` on the balance plus the ledger `INSERT`), so concurrent requests can't lose a balance change. To reset, drop and recreate the database. To carry over an old `backend/data.json`, run `npm run db:import` against an empty database before the first server start; it refuses to run on a non-empty one. Authentication: passwords are bcrypt-hashed (`users.password_hash`; a legacy plaintext `password` column is converted and dropped on first start). Login/register return a JWT (`JWT_SECRET` required in `backend/.env`, lifetime `JWT_EXPIRES_IN`, default 8h) sent as `Authorization: Bearer`. `middleware/auth.js` (`requireAuth`, `requireRole`) re-reads the user row on every request, so deactivation, deletion, role change and password change/reset (which bump `users.token_version`) revoke tokens immediately. Login is throttled in memory (5 failures per username → 15 min block, 429). `lowdb` is listed in `package.json` but unused. Password rule (new/changed passwords only): 8+ chars with a letter and a number.

Endpoints (all except register/login need a Bearer token): `POST /api/register`, `POST /api/login` (401 generic message, 429 when throttled), `GET /api/me`, `PUT /api/me/password`, `GET /api/history/:userId` (last 10; Passengers only their own), `GET /api/routes` (admins see all routes, passengers only active ones), `POST /api/routes` and `PUT /api/routes/:id` (admin; `name`, `fare`, `status`, `stations` as names, `version` required on PUT, 409 when stale), `GET /api/routes/history` (admin audit trail), `POST /api/topup` (passenger, own card only; body `amount`), `POST /api/rfid/tap` (admin; body `{userId, action: 'start'|'end', routeId, stationId}`; start checks balance >= the route's fixed fare and opens a trip, end debits that fare once and completes it; 402 insufficient balance, 403 deactivated card, 409 trip state conflicts), `GET /api/trips/mine`, `GET /api/trips` (admin; `?status=&userId=`), `PUT /api/trips/:id/cancel` (admin; `reason`), `GET /api/trains` (live positions with `signal`/`status`; `no_signal` after `TRAIN_SIGNAL_TIMEOUT_SECONDS`, default 300) and `POST /api/trains/position` (admin-authenticated GPS feed). Admin user management lives in `routes/users.js` under `/api/users`: `GET` (`?search=&role=`), `POST`, `PUT /:id` (username/role), `PUT /:id/status`, `POST /:id/reset-password`, `DELETE /:id` (anonymising soft delete, only when balance is 0). Admins cannot deactivate/delete/demote themselves or the last active admin. The tap endpoint is the bridge for future Arduino/ESP32 hardware on the local network (device authentication is not designed yet); the admin dashboard simulates taps through it. Route/trip/train code lives in `routes/railRoutes.js`, `routes/trips.js`, `routes/trains.js`.

**Online top-ups and reader taps.** Passengers top up through PayHere (Sri Lanka gateway, hosted checkout, LKR, whole rupees between `TOPUP_MIN` 500 and `TOPUP_MAX` 50000). `POST /api/topups` (`amount`) creates a `topups` row and returns `checkout: { url, fields }` (signed form fields the browser POSTs to PayHere; `order_id` is the top-up id); `GET /api/topups/mine`, `GET /api/topups/:id` (status + balance, polled after the return redirect), `POST /api/topups/:id/cancel`, `GET /api/topups/config`, and `GET /api/topups` (admin; `?status=&userId=`). The Balance is credited only by `settleTopup` in `lib/topups.js`, called from PayHere's server notification `POST /api/payhere/notify` (form-encoded, verified by `md5sig`; `status_code` 2 = paid). It is exactly-once (row lock, `payment_events` replay table, unique `transactions.topup_id`); amount/currency mismatches or inactive accounts become `review` (admin attention, not credited). Env: `PAYHERE_MERCHANT_ID`, `PAYHERE_MERCHANT_SECRET`, `PAYHERE_SANDBOX` (sandbox unless `false`), `PAYHERE_NOTIFY_URL` (public URL, e.g. an ngrok tunnel; PayHere cannot reach localhost, so without it top-ups stay pending), `FRONTEND_URL`, `TOPUP_MIN/MAX`, `TOPUP_PENDING_MINUTES`. With `PAYHERE_APP_ID`/`PAYHERE_APP_SECRET` (Payment Retrieval API) `GET /api/topups/:id` also asks PayHere whether a pending attempt was paid (same dedupe key as the notification), so top-ups complete without a public notify URL. Without merchant credentials the endpoints return 503. The legacy no-payment `POST /api/topup` returns 403 unless `ALLOW_DEMO_TOPUP=true`. `stripe_*` columns/table are unused legacy.

Reader taps: `POST /api/device/tap` (`routes/device.js`, auth by `X-Device-Key`, not JWT; body `{cardUid, eventId, action?}`). A device (`devices` table, key stored as SHA-256, shown once on create/rotate) is bound to one Route and Station; cards (`cards` table, UID to Passenger) are managed by admins. `eventId` makes taps idempotent (replay returns the stored body with `Idempotent-Replay: true`); rejections are logged in `tap_events` (list: `GET /api/rfid/events`). Omitted `action` is inferred from the open trip. Errors carry a stable `code` (`unknown_card`, `insufficient_funds`, `open_trip_exists`, ...). Admin endpoints: `/api/cards`, `/api/devices` (+ `PUT /:id/status`, `POST /:id/rotate-key`). Both the admin simulator (`/api/rfid/tap`) and readers go through `lib/tap.js` `applyTap`; trips record `start_source`/`end_source` (`admin` or `reader`).

Data shapes: users have `{id, username, role: 'user'|'admin', balance, status: 'active'|'deactivated'|'deleted', fullName, phone, nic, email, createdAt}` (contact fields are required at Passenger registration, optional for seeded/Admin-created accounts, unique for email and NIC, and cleared on delete; validation lives in `backend/lib/profile.js`) (the hash is never returned). Transactions have `{id, userId, type: 'credit'|'debit', title, amount, date}`, where `date` is a display string formatted from the stored `created_at` timestamp. `amount` for top-up and tap must be a number > 0 (else 400). Routes have `{id, name, fare, status: 'active'|'inactive', version, stations: [{id, name, position}]}` (one fixed fare per trip; the old `base_fare`/`per_km`/`total_km`/`stations` columns are legacy and unused). Trips have `{id, userId, routeId, startStation, endStation, fare, status: 'open'|'completed'|'cancelled', startedAt, endedAt}`; the fare is snapshotted when the trip starts and at most one trip per card can be open.

**Frontend (`frontend/src`).** `main.jsx` wraps the app in `BrowserRouter`, and `App.jsx` maps `/login`, `/dashboard` (passenger), `/admin` and `/routes` (live tracking board). Each page is a self-contained component in `src/pages/`. There's no shared API client, context or store:
- API calls go through `src/api.js` (axios instance; base URL `VITE_API_URL`, default `http://localhost:5000`). It attaches the Bearer token and, on any 401 from a protected call, clears the session and redirects to `/login` with a flash message. Session helpers (`setSession`, `clearSession`, `getStoredUser`) live there too.
- Session state is `localStorage` keys `user` (JSON) and `token`. `components/RequireAuth.jsx` wraps `/dashboard` (role `user`), `/admin` (role `admin`) and `/routes`; it confirms the session with `GET /api/me` before rendering, so editing `localStorage` doesn't grant access. After a top-up, `Dashboard` writes the new balance back into the `user` object.
- `Routes.jsx` is the passenger view: read-only routes and fares from `/api/routes`, plus the live tracking board polled from `/api/trains` (empty "Awaiting GPS" state until a position is posted). Admin Routes & Pricing and the RFID terminal live in `components/admin/`.

**PWA and offline.** `vite-plugin-pwa` (configured in `frontend/vite.config.js`) generates the manifest and a Workbox service worker that precaches the app shell (not `edit.mp4`) and serves `index.html` for every in-app route. It is registered from `components/UpdatePrompt.jsx` in prompt mode: a new deploy shows a "new version" toast, and a waiting version otherwise applies on the next launch. `npm run dev` has no service worker. API responses are never cached by the service worker. Instead, `lib/offlineCache.js` keeps a per-Passenger `localStorage` snapshot (`offline:<userId>`: history, trips, top-ups, routes and `savedAt`; no contact details, no train positions, nothing for Admins). Offline views read it and label it "last updated". `clearSession()` removes all snapshots, and a new sign-in removes other users' snapshots. `lib/network.js` + `hooks/useOnlineStatus.js` track connectivity (a request with no response also counts as offline). The `api.js` request interceptor rejects every non-GET while offline (`code: 'OFFLINE'`; show it with `errorMessage(err, fallback)`), so nothing is queued. Offline, `RequireAuth` renders with the stored user and status `'offline'` (read with `useSessionStatus()`), then re-checks `/api/me` on reconnect. Admin pages show a "needs a connection" panel offline. `components/InstallPrompt.jsx` offers installation on Login and the Passenger dashboard (iOS gets Add to Home Screen steps). Testing on a phone needs HTTPS: build with `VITE_API_URL` pointing at a tunnelled backend, run `npm run preview -- --host` behind an HTTPS tunnel (e.g. ngrok), and set `FRONTEND_URL` to that origin so PayHere returns to the app. On iOS the PayHere return often opens in Safari rather than the installed app. The Balance is still correct the next time the app opens.

**Mobile layout.** Pages must work from 320px wide. The Admin sidebar is a drawer below `md` (header menu button). Wide tables scroll inside their own `overflow-x-auto` wrapper. Dialogs use `modal-max-h overflow-y-auto` and top-align on phones. Safe-area utilities (`pt-safe`, `pb-safe`, `pl-safe`, `pr-safe`) live in `index.css`. Framer Motion respects reduced motion via `MotionConfig` in `main.jsx`.

**Styling.** Tailwind with a custom `rail` palette (`rail-blue`, `rail-red`, `rail-dark`, `rail-muted`), `outfit`/`inter` font families, and tightened border radii, all set in `frontend/tailwind.config.js`. Animations use Framer Motion, and icons come from lucide-react. The project's design notes (`smartrail-ticketing.md`) call for a strict "no purple" palette. PWA manifest and service-worker settings are in `frontend/vite.config.js`. Icons are generated from `frontend/public/logo.svg` (`frontend/pwa-assets.config.js`).
